# Owner v1 最小验收

本表只记录三项目共享 RTX 4080 所需的最小闭环，区分离线证据和真实任务结果。项目保存自己的任务、重试和产物；协调器只保存 FREE、OWNED、UNKNOWN 以及 acquire、release、observe

## 范围与切换前提

- 首次让任何项目在生产中获取 Owner 前，三个项目的最低公共 GPU 入口都必须接受同一门禁；尚未迁移的项目可以继续排队或暂时停止 GPU 取队列，不能保留会在新 Owner 持有时自行启动的旧直连入口
- H3、Live、Manga 按此顺序各完成一个真实业务闭环；每个项目通过后立即删除该项目已无用途的旧 Broker 强依赖，再推进下一项目
- 项目观察端只向协调器报告本项目能否交接及入口是否已封闭；模型和后端细节由项目内部核实。整卡采样用于确认安全交接与发现矛盾，不建立每任务显存画像
- 公网旧 Broker 的 502 与未知退出码留在旧服务运行记录中。旧准入职责被 Owner 替代后，它们不构成 Owner v1 的上线门槛；公网监控是否可用也不决定本机模型任务能否继续

最低门禁的位置已经按现有调用链核对：H3 是公共 Comfy 提交点加 Comfy `/prompt` 入口，Live 是 Agent 领取 Core GPU 工作后的 Owner 窗口加 Worker 实际 GPU 调用入口，Manga 是独立语义服务 `/segment` 与 FLUX 服务 `/generate`。后续功能从这些入口进入即可，不为每种视频、录音或页面功能增加一套 Owner 协议。未覆盖的 CUDA 入口在 Owner 模式下必须明确拒绝

## 必须通过的闭环

| 场景 | 已有证据 | 尚须完成的真实验收 |
| --- | --- | --- |
| 同时获取与三态恢复 | 假项目并发、重启和故障回归已通过；Core 对缺失的可选诊断细项不再额外卡死释放，对明确矛盾事实仍冻结新工作。正常状态改为只采相关项目与整卡的离线回归已通过 | 用真实项目观察端确认同一时刻只有一个 Owner；无关项目停机不阻断稳定交接；申请者或当前 Owner 失联则进入 UNKNOWN，只有四路新鲜事实可恢复 |
| H3 完整视频 | 桥接、Comfy 门禁和失联保护已有离线回归；普通视频在 Comfy 确定终态、封门及卸载后释放 Owner，再做 CPU／网络收尾。H3 工作区已修正业务完成时机，下载失败、任务状态写入失败与重复轮询的定向回归通过，尚未在生产进程与真实视频验证 | 原 H3 API 完成一个视频：获取 Owner、提交一个可追踪的 Comfy 工作、确认最后一次 4080 工作终态并安全释放；本地成品与 take 保存成功后业务任务才显示 completed。协调器故障不得取消已提交工作。真实闭环后删除该路径旧 permit、session、profile 和心跳取消强依赖 |
| Live 录音到模型结果 | Core、Agent、Worker 的 Owner 路径和结果恢复已有离线测试；旧 Worker 的模型仍驻留。当前 Owner 启动脚本强制独立模型文件目录，必要性未获实测支持 | H3 持有时录音保存并确认，GPU 阶段等待且不耗尽业务重试；H3 释放后原队列继续、结果只写一次、模型卸载并释放 Live Owner。核对服务进程、端口和模型驻留，物理复制权重不作为默认门槛。通过后删除该路径旧 Broker 准入强依赖 |
| Manga 原创单页 | 主项目、语义和 FLUX Worker 门禁已有离线回归；尚无真实页面证据 | 原创单页完成实际语义和图像 GPU 工作、成品可读、后端停止并安全释放；通过后删除该路径旧 Broker 准入强依赖 |
| 运行中故障 | 离线测试覆盖 UNKNOWN 禁新任务及已提交工作继续的逻辑 | 一个已提交的 GPU 工作运行时使协调器不可用：原工作继续，新工作等待；恢复时只根据项目与整卡的新鲜直接事实返回 OWNED 或 FREE |

H3 的其他功能与完整多阶段功能矩阵不属于本轮逐项验收。它们若进入同一个 GPU 后端，应由最低公共入口门禁覆盖；暂时无法覆盖的入口必须在 Owner 模式明确拒绝，不能绕门。正常路径不再每次询问无关项目，因此三项目所有最低 GPU 入口都已封门是**代码安全前提**，必须逐入口验证，不能只凭 Owner Core 离线测试宣布生产可用

Live 的独立 Ollama 进程和端口可让模型驻留与卸载归属于 Live；`OLLAMA_MODELS` 只指定磁盘存储位置，物理复制权重本身不能证明显存已释放。是否可与另一进程共用同一模型库须另行实测，不能把尚未验证的只读共享目录当成已可生产使用的配置

## 逐项目删除账

| 项目 | 真实闭环后立即删除的旧准入强依赖 | 保留的项目职责 |
| --- | --- | --- |
| H3 | `broker_bridge` 中对应视频路径的 job／session／permit／profile、心跳失联取消和旧 Broker 恢复写入；待其他 Comfy 入口封门后删除剩余旧准入分支 | H3 幂等编号、原任务队列、Comfy 轮询、明确取消、业务重试和成品保存 |
| Live | Agent 的 Broker permit 与状态镜像、Worker 的旧 permit／profile 验证、Broker 令牌及模式启动分支 | Core 持久任务、录音 ACK、业务租约、结果写回、Worker 模型运行与卸载 |
| Manga | `gpu_broker.py` 的 job／stage journal／permit／profile、Worker 的旧 permit 验证和 `18765` 启动配置 | Manga 页面队列、原创素材、业务暂停／取消、语义与 FLUX 原推理及成品保存 |

删除发生在各自真实闭环通过后，不预先拔掉当前仍在工作的旧路径。三项目完成后先永久关闭旧共享准入写入，再删除 Owner 启动时读取旧 `broker.sqlite3` 的 `allocation_enabled` 检查和旧 Broker 用 `owner.json` 存在性阻止启用的过渡互锁；届时由各项目入口封闭、Owner 三态与直接观察守住准入。旧监控可保留为只读，不能再决定新 GPU 工作是否开始

## 完成判定

每个真实闭环保留项目任务编号、后端执行编号、产物或结果、Owner 获取与释放记录、必要的项目观察及整卡交接数据。无需把每个内部诊断字段做成统一的四项证明清单

最终同时交付三项目真实结果、每项目删除的旧依赖、仍存在但已退出 GPU 准入关键路径的旧组件，以及重构前后主路径步骤和代码依赖的对比。Owner 能跑但旧 Broker 的强依赖仍完整保留时，不标记重构完成
